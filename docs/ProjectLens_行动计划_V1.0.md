## 2. 里程碑规划（建议）

> 说明：以下以“周”为单位，你可以按团队人力调整；每个里程碑都定义了必须能演示的“验收口径”。

### 2.1 M0：文档与工程基线（1 周）

**目标**
- 明确目录结构、文档生成方式、最小运行链路（即使只是 CLI 工具链）

**主要工作**
- 确定目标运行形态：桌面（Tauri/Electron）或 Web（React+API）或纯 CLI（先打通处理链路）
- 约定项目输入目录结构与阶段识别规则（调研/蓝图/设计/开发/测试…）
- 约定“证据链”字段规范（chunk 定位、引用格式）
- 接入 `epic-doc` 的文档输出流水线（JSON config -> docx）

**验收口径**
- 能把任意 Markdown 报告模板用 `epic-doc` 生成 docx（至少含：标题、段落、表格、页眉页脚、目录）

### 2.2 M1：文档索引与预览 MVP（2-3 周）

**目标**
- 把项目文件夹变成“可浏览、可搜索、可增量同步”的项目

**主要工作**
- 项目创建、目录扫描、增量同步（sha256/mtime）
- `.md/.txt` 解析与结构化（先保证稳定）
- 文档预览：目录树、全文搜索、章节大纲（前端或 CLI 输出均可）
- chunk 切分与定位信息（段落 id/偏移）

**验收口径**
- 同步后能看到每个文档的状态（indexed/chunked…）
- 任意 chunk 都能回链到原文位置（至少段落级别）

### 2.3 M2：AI 提取与标注 MVP（3-4 周）

**目标**
- 打通“分析任务 -> 标注 -> 审阅 -> 导出为 Markdown 报告草稿”

**主要工作**
- LLM Gateway（统一 provider 接口、超时/重试、token 统计）
- 任务编排：按文档/按 chunk 并行执行，支持 partial_success
- 标注模型：需求/风险/决策/依赖/知识点（最小字段）
- 标注审阅：确认/驳回/编辑/验证

**验收口径**
- 一次分析任务能产出可追溯证据的标注（每条标注含来源）
- 失败可重试（仅重试失败文档/失败 chunk）

### 2.4 M3：评审报告生成 MVP（2-3 周）

**目标**
- 形成“模板化报告 + 证据引用 + docx 导出”的闭环

**主要工作**
- 报告模板（章节结构 + 检查清单）
- 报告编辑器（最小：章节可编辑、引用标注可插入）
- `epic-doc` 导出：docx（优先），pdf/html（可选，依赖 pandoc）
- 报告版本与冻结（审计基线）

**验收口径**
- 报告 docx 能生成：封面、目录、章节、表格（检查清单/风险矩阵）、引用块
- 冻结版本后不可被自动重写，且可复制出新版本继续编辑

### 2.5 M4：跨文档一致性与知识库（4+ 周）

**目标**
- 从“单项目分析”升级为“跨项目复用与标准化评审体系”

**主要工作**
- 向量库与语义检索（行业洞察、相似案例）
- 脱敏与权限：跨项目检索只输出脱敏片段
- 指标体系：健康度评分（覆盖率、风险、追溯完整性）

**验收口径**
- 同行业历史项目能产出“高频需求/高频风险/典型交付物”并可解释样本来源

## 3. 行动分解（可直接开工的任务列表）

### 3.1 文档与模板

- 定义报告模板：全项目分析、阶段性评审、Go/No-Go 门禁
- 定义引用格式：`[doc:xxx][chunk:yyy]` 或脚注式
- 建立 `epic-doc` JSON 模板目录与生成命令

### 3.2 数据与证据链

- 定义 `ParsedDocument` 结构：标题/段落/表格/图片占位
- 定义 `Chunk.locator_json`：段落 id、偏移、页码（可选）

### 3.3 LLM 与任务编排

- Provider 接口：Claude/Qwen/MiniMax/Ollama（先 1 个实现）
- 任务状态机：queued/running/partial_success/succeeded/failed/cancelled
- 可重试策略：超时/限流/解析失败

### 3.4 报告导出（仅调用 epic-doc）

- 报告内容 JSON → epic-doc blocks（映射规则）
- 统一导出接口：docx 必须、pdf/html 可选

## 4. 风险与对策（提前声明）

- **输入文档格式复杂**（docx/pdf/xlsx）：先从 md/txt 开始，逐步扩展；每扩展一种格式，必须补齐定位/证据链。
- **长耗时任务体验差**：必须有任务队列与可解释进度；允许 partial_success 与重试。
- **证据链断裂**：任何无法定位的结论都必须标记 `needs_review`，不允许当作确定性结论进入最终报告。
- **权限与脱敏**：跨项目知识库默认只读+脱敏；原文访问需授权与审计。

## 5. 对 `epic-doc` 的具体需求（你可转给他们）

为了更顺畅地“直接调用 epic-doc 创建文档”，建议 `epic-doc` 支持：

- **更完整的 JSON Schema**：补齐每种 block 的字段定义与校验
- **validate 能给出明确错误定位**：例如某个 table block 的列宽缺失
- **支持 block 元数据**（不会渲染也行）：用于保留证据链（doc/chunk/offset）
