# **第一章  产品概述**

## **1.1  产品背景**

在 IT 咨询与系统实施领域，顾问团队每天需要处理海量的项目文档——调研记录、业务蓝图、功能配置清单、任务看板导出等——并从中提炼洞察、发现风险、输出评审意见。当前，这一过程几乎完全依赖人工阅读和经验判断，存在以下显著痛点：

- 文档体量大：一个中型 MES 项目通常产生 20 万字以上的交付物文档，完整阅读耗时数天。
- 知识沉淀难：每次项目积累的洞察仅存在于个人记忆，难以结构化复用于下一个项目。
- 评审质量参差：评审结论依赖顾问个人能力，缺乏系统化的检查框架，容易遗漏关键风险。
- 跨行业迁移慢：顾问进入新行业时缺乏行业最佳实践参照，学习曲线陡峭。

## **1.2  产品定位**

**ProjectLens** 是一款面向 IT 实施顾问、项目经理和售前团队的**智能项目分析与评审平台**。它以大语言模型为核心引擎，以结构化的项目知识库为基础，帮助用户快速从项目文档中提取关键信息、识别风险、生成专业评审报告。

### **1.2.1  通用业务文档审查定位（补充）**

除项目交付实施场景外，ProjectLens 的定位进一步扩展为“**通用业务关联性文档审查平台**”。系统通过**审查技能包**内 `review_domain.md` 可配置的关注点与 Prompt 驱动审查逻辑，使其可应用于更多业务文档体系：

- 合规/内控文档：制度条款覆盖、职责边界、证据留痕、审计追溯。
- 合同/招采文档：交付范围、验收标准、违约责任、变更控制。
- 产品/运营文档：需求边界、流程例外、指标口径一致性、执行闭环。
- 数据治理文档：主数据责任、字段口径、质量规则与一致性检查。
- 架构/接口文档：依赖关系、异常与降级策略、跨系统一致性约束。

该能力边界由**当前活动审查技能包**内的 `review_domain.md` 定义，不与某一行业或交付阶段强绑定。

### **1.2.3  当前实现范围（以代码为准）**

本仓库当前 Web 形态（M0/M1）聚焦“单项目目录 → docs2md 转换 → 索引与分块 → 流式审查输出”的闭环能力，核心包括：

- 项目：选择/注册项目目录（可选本机文件夹选择器）
- 设置：`chunk_limit`、分块策略（空行 / Markdown 结构感知）、规则（关注点与预设组合）、模型（文本与 VL）
- 一键流程：转换（docs2md）→ 索引与分块 → 模型流式分析（SSE）
- 证据追溯：输出中“片段与来源索引”（片段编号、文件、章节、行号范围）
- 会话：按项目保存会话（conversation）与分析运行记录，支持基于上次结果的追问（SSE）
- 导出：导出 Markdown；以及将分析映射为 `epic-doc` 配置并生成 docx（仅调用 `epic-doc`，本项目不实现排版引擎）

本《需求与设计文档》早期章节包含较多“产品愿景”模块（知识库、任务队列、向量库、仪表盘等）。若与本节冲突，以本节与代码实现为准；未实现内容应视为后续规划，而非当前可用功能。

### **1.2.2  规则文件与「组合使用建议」（配置约定，与实现对齐）**

- **活动审查域文件**：唯一配置源为**当前活动审查技能包**内 `review_domain.md`（目录：`review_skill_packages/<package_id>/review_domain.md`；包根可由 `AIKA_REVIEW_SKILL_PACKAGES_ROOT` 覆盖）。
- **关注点**：以 `### focus:<id> | <名称>` 定义可配置审查维度，正文为 Prompt。
- **组合使用建议**：在活动规则文件中以二级标题「组合使用建议」引导 **固定五列** Markdown 表（评审节点、推荐组合的关注点、审查角色、审查目标与原则、输出要求），用于推导首页可选预设及非空的审查角色/原则/输出约定；推荐列以 `` `focus:id` `` 引用关注点 id。详细格式与界面行为见《ProjectLens_功能设计_V1.1.md》《ProjectLens_详细设计_V1.1.md》及《User_Manual_zh.md》。

## **1.3  核心价值主张**


| 维度      | 价值说明                                           |
| ------- | ---------------------------------------------- |
| 效率提升    | 文档分析时间从数天压缩至数小时，报告生成从半天压缩至分钟级                  |
| 知识资产化   | 每个项目的经验教训沉淀为可检索、可复用的结构化知识                      |
| 评审标准化   | 内置多行业最佳实践检查清单，评审质量不再依赖个人经验水平                   |
| AI 可配置化 | 支持接入 Claude、Qwen、MiniMax 等主流大模型，满足不同企业的合规与成本需求 |


# **第二章  目标用户与使用场景**

## **2.1  用户角色**


| 角色        | 主要职责             | 核心诉求               |
| --------- | ---------------- | ------------------ |
| 实施顾问      | 主导项目调研、蓝图设计、开发管理 | 快速掌握项目全貌，识别需求缺口    |
| 项目经理      | 项目进度与质量管控        | 自动化生成评审报告，监控项目健康度  |
| 售前顾问 / 销售 | 行业方案宣讲、客户需求对标    | 按行业获取参考案例和解决方案建议   |
| 质量评审专家    | 第三方项目评审，识别风险     | 使用标准化检查清单，输出专业评审意见 |
| 知识管理员     | 维护组织级知识库         | 管理项目标注、知识图谱的质量和一致性 |


## **2.2  典型使用场景**

### **场景 A：调研结束后快速生成业务蓝图初稿**

顾问完成客户调研，将调研记录文档放入项目文件夹。ProjectLens 自动解析文档，提取业务需求点，与同行业历史项目对比，指出本次调研覆盖的盲区，并生成蓝图初稿结构建议，顾问只需在此基础上补充细节。

### **场景 B：项目中期评审风险识别**

项目执行到蓝图完成阶段，项目经理在 ProjectLens 中启动评审，系统自动分析：需求从调研到蓝图的覆盖率、任务分解与需求的映射关系、接口设计完整性等，生成带有具体证据引用的风险报告。

### **场景 C：售前行业方案咨询**

销售准备拜访某汽车制造商，在 ProjectLens 中输入"汽车 MES"行业，系统从知识库中检索相关项目案例，给出常见需求模式、高风险模块、典型交付物清单和定价参考。

### **场景 D：项目竣工评审报告生成**

项目验收前，质量评审专家选择目标项目，指定报告模板（类似附件示例），系统自动分析各阶段交付物，逐章生成评审报告，专家只需审阅和修改，最后一键导出为专业格式的 Word 文档。

### **场景 E：通用业务制度与合规材料审查（扩展）**

组织可将制度、流程、合规与审计材料导入统一目录，通过自定义**审查技能包**（编辑包内 `review_domain.md` 的关注点，如“职责边界”“控制点覆盖”“证据完整性”）执行审查。系统输出结构化问题清单与证据引用，支持形成内控评估报告。

### **场景 F：合同与招采文档一致性审查（扩展）**

在招采或合同评审阶段，系统按关注点组合（如“交付物与验收”“违约条款”“范围变更”）自动检查文档间一致性，识别条款缺失、责任不对称与范围蔓延风险，生成可追溯的审查结论。

# **第三章  功能需求详述**

## **3.1  模块一：项目与文档管理**

### **3.1.1  文件夹结构规范**

系统支持用户指定本地或云端文件夹作为项目根目录。规范的目录结构如下：


| 约定目录结构 项目根目录/ ├── 01调研/ │ ├── 业务调研记录v1.0.md │ └── IT系统调研记录v1.0.docx ├── 02蓝图/ │ ├── 基础数据模块蓝图v3.0.md │ └── 生产执行模块蓝图v3.0.md ├── 03设计/ ├── 04开发/ ├── 05测试/ ├── 06上线/ └── 07复盘/ |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |


系统同时支持自定义阶段名称，并自动识别常见的阶段命名模式（如"调研"/"Research"/"Survey"均可识别为调研阶段）。

### **3.1.2  文档格式支持**


| 格式              | 支持级别 | 说明                    |
| --------------- | ---- | --------------------- |
| .md / .markdown | 完全支持 | 首选格式，解析精确             |
| .docx / .doc    | 完全支持 | 通过 pandoc 转换为结构化内容    |
| .pdf            | 完全支持 | 文本型 PDF；扫描件需开启 OCR 选项 |
| .txt            | 完全支持 | 纯文本，按段落分割             |
| .xlsx / .csv    | 部分支持 | 提取表格内容作为结构化数据         |
| .pptx           | 部分支持 | 提取文字和备注内容             |


### **3.1.3  项目索引与快照**

- 首次加载项目目录时，系统构建文档索引（文件名、阶段、修改时间、字符数、摘要），后续增量更新。
- 支持为项目打标签（行业、规模、技术栈等），用于知识库的跨项目检索。
- 支持创建项目快照，记录某一时间点的文档集合状态，方便回溯历史版本对比。

## **3.2  模块二：智能内容提取与标注**

### **3.2.1  自动提取**

系统在用户授权分析后，调用 LLM 对每个文档进行结构化提取，提取维度包括：


| 提取维度 | 说明                                 |
| ---- | ---------------------------------- |
| 需求条目 | 识别具体的业务需求，标注优先级（明确需求/待确认/超出范围）     |
| 风险信号 | 检测"暂不确认"/"待讨论"/"超出范围"等语义标记，及隐性风险描述 |
| 决策点  | 识别需要客户确认或多方达成共识的关键决策               |
| 依赖关系 | 识别模块间、系统间的接口依赖和数据流向                |
| 时间承诺 | 提取含时间节点的承诺语句，如"上线前完成X"             |
| 实体识别 | 提取人名、系统名、模块名、业务术语，建立项目词汇表          |
| 章节摘要 | 每个文档/章节生成100字以内的结构化摘要              |


### **3.2.2  标注系统**

提取结果以高亮卡片的形式呈现，用户可以：

- 确认/拒绝：对 AI 提取的每个条目进行确认或标记为无效。
- 编辑内容：直接修改条目的文字描述和分类标签。
- 添加注释：在条目上附加顾问个人的评注（支持 Markdown）。
- 关联原文：每个提取条目链接到源文档的具体段落（支持一键跳转查看原文）。
- 手动添加：用户可在任意文档位置手动高亮选中文字并创建标注。
- 批量操作：支持多选条目进行批量分类、批量导出。

### **3.2.3  标注类型体系**


| 标注类型   | 图标/颜色 | 含义          | 典型示例        |
| ------ | ----- | ----------- | ----------- |
| 需求-明确  | 🔵 蓝色 | 已确认纳入范围     | 工单下发功能      |
| 需求-待确认 | 🟡 黄色 | 调研有记录但方案未承接 | 线边库拉动配送     |
| 需求-超范围 | ⚫ 灰色  | 已确认不实施      | SPS 线边配送    |
| 风险-高   | 🔴 红色 | 可能导致项目失败的风险 | 接口未联调即上线    |
| 风险-中   | 🟠 橙色 | 影响交付质量的风险   | 验收标准未定义     |
| 风险-低   | 🟢 绿色 | 值得关注的改进点    | 工时估算偏低      |
| 决策-待定  | 🔷 深蓝 | 需客户/多方确认    | 权限矩阵设计      |
| 知识点    | ⭐ 金色  | 可复用的行业洞察    | MES 九阶段实施框架 |


## **3.3  模块三：方案助理**

### **3.3.1  行业洞察检索**

顾问或销售在侧边栏选择或输入行业（如"汽车制造/MES"、"医疗器械/PLM"），系统从知识库中检索相关项目经验，返回：

- 该行业常见业务需求模式（Top 20 高频需求）。
- 历史项目中的高频风险模式（Top 10 风险类型）。
- 典型交付物清单和建议文档模板。
- 可参考的方案章节片段（脱敏后）。

### **3.3.2  需求审查**

基于已加载的项目文档，系统执行以下分析：

1. 需求完整性检查：与同行业典型需求集对比，识别可能被遗漏的需求模块。
2. 需求-方案一致性检查：逐条比对调研阶段记录的需求与蓝图方案中的功能描述，标记断层。
3. 需求-任务追溯检查：检查任务管理系统（禅道、Jira 等，通过 API 或导出文件接入）中的任务是否能追溯到蓝图需求。
4. 范围蔓延分析：识别蓝图完成后新增的需求，分析对项目的影响。

### **3.3.3  项目管理问题诊断**

系统分析项目任务数据（可从禅道/Jira 导出文件导入），生成以下诊断报告：

- 任务时序分析：按任务创建时间分布识别"上线后才发现需求"模式。
- 工时合理性分析：对比同类任务工时，识别严重低估或高估的任务。
- 里程碑缺失检测：识别关键里程碑前后的任务缺口（如上线前未见接口测试任务）。
- 人员风险分析：识别关键人员集中度（单点依赖）、交接记录等。

## **3.4  模块四：项目评审助理**

### **3.4.1  评审报告生成流程**

用户选择评审模板（内置或自定义），系统按以下流程生成报告：


| 步骤  | 操作        | 说明                                 |
| --- | --------- | ---------------------------------- |
| 1   | 选择项目 评审范围 | 指定要评审的项目和阶段范围（如"调研到蓝图"、"全项目"）      |
| 2   | 选择报告模板    | 内置模板：需求覆盖评审、风险矩阵评审、验收准备就绪评审，支持自定义  |
| 3   | AI 分析执行   | 系统并行调用 LLM 分析各文档，汇聚提取结果，执行跨文档关联分析  |
| 4   | 草稿预览与编辑   | 在 Web 界面预览报告结构，支持拖拽调整章节顺序，直接编辑段落内容 |
| 5   | 导出报告      | 支持导出为 .docx（含图表）、.pdf、.md 格式       |


### **3.4.2  内置报告模板**

**模板一：全项目分析报告（对标附件示例）**

结构如下：

- 执行摘要（项目基本信息、核心发现、总体评分）
- 第一部分：调研到方案——需求承接分析（需求覆盖率热图、断层清单）
- 第二部分：方案到任务——开发覆盖分析（任务分解完整性、工时分布图）
- 第三部分：任务时序分析（创建时间分布图、关键里程碑缺失分析）
- 第四部分：评审检查清单（逐条列示检查项，标注通过/待确认/不通过）
- 第五部分：改进建议（分优先级，含具体行动建议）

**模板二：轻量评审报告（阶段性检查）**

- 调研阶段完成评审：需求完整性、调研深度、待确认事项
- 蓝图阶段完成评审：方案覆盖率、验收标准定义、权限矩阵完整性
- 上线前 Go/No-Go 评审：接口联调状态、培训完成率、P0 问题关闭率

### **3.4.3  报告质量控制**

- 所有 AI 生成的结论均标注信息来源（链接到原文段落）。
- 支持"置信度"标注：高置信（有直接文字依据）/ 中置信（推断）/ 需人工核实。
- 评审人可在报告中添加批注（类似 Word 批注功能），导出时保留。
- 支持版本对比：同一项目不同时间生成的报告可进行差异对比。

# **第四章  技术架构设计**

## **4.1  整体架构概览**

## **4.4  LLM 网关层（核心设计）**

### **4.4.1  设计原则**

- 统一接口：所有 LLM 通过统一的 Provider 接口调用，上层代码不感知底层模型差异。
- 热切换：运行时可在 UI 中切换模型提供商，无需重启服务。
- 失败降级：主模型不可用时自动切换到备用模型。
- 成本追踪：记录每次调用的 token 消耗，支持按项目统计费用。

### **4.4.2  支持的 LLM 提供商**


| 提供商              | 推荐模型                 | 优势                  | 适用场景       |
| ---------------- | -------------------- | ------------------- | ---------- |
| Anthropic Claude | claude-sonnet-4      | 长文档理解能力强，中文能力优秀     | 全项目分析、复杂推理 |
| 阿里云 Qwen         | qwen-max / qwen-long | 超长上下文（1M token），价格低 | 大文档处理，批量分析 |
| MiniMax          | MiniMax-Text-01      | 中文优化，API 稳定         | 国内合规要求场景   |
| OpenAI           | gpt-4o               | 综合能力强，生态完善          | 通用场景       |
| 本地模型             | Ollama Qwen2.5       | 完全离线，数据不出境          | 数据高度敏感场景   |
| 自定义 API          | 任意 OpenAI 兼容接口       | 兼容现有企业内部 LLM        | 企业私有化部署    |


### **4.4.3  LLM 配置 UI 规范**

在"设置 → AI 模型配置"页面，用户可配置：

- **默认模型：**选择全局默认的 LLM 提供商和模型。
- **任务级覆盖：**为不同任务类型（文档摘要/风险提取/报告生成）分别指定模型。
- **API 密钥管理：**加密存储在本地 KeyChain 或服务器端加密存储；支持多密钥轮换。
- **代理配置：**支持配置 HTTP 代理，满足企业网络要求。
- **请求参数：**temperature、maxtokens、timeout 等参数可按任务类型调节。
- **连接测试：**配置完成后一键测试连通性和响应时间。

# **第六章  提示词工程规范**

## **6.1  提示词分层架构**

系统提示词分为三层，以实现灵活的定制和复用：

- **系统级提示词（System Prompt）：**定义 AI 的角色（资深 IT 实施顾问）、分析原则（基于证据、标注来源、区分高/中置信度）。不可被用户修改。
- **任务级提示词模板（Task Template）：**每类分析任务（需求提取、风险识别、报告生成等）有对应的提示词模板。内置模板不可删除，但用户可克隆后修改，或新建自定义模板。
- **上下文注入（Context Injection）：**每次调用时动态注入项目信息（行业、规模）、相关历史标注、文档片段等。

## **6.2  核心提示词示例**

### **6.2.1  需求提取提示词模板**

| Prompt: requirementextractionv1 你是一位资深 IT 实施顾问，正在分析 {industry} 行业的 {projectname} 项目文档。 请从以下文档片段中提取所有业务需求条目，并按如下 JSON 格式输出： {   "requirements":      {       "id": "req001",       "content": "需求的简洁描述（50字以内）",       "originaltext": "原文引用（30字以内）",       "status": "confirmed|pending|outofscope",       "priority": "p0|p1|p2|p3",       "module": "所属业务模块",       "confidence": "high|medium|needsreview",       "risksignals": "风险信号1", "风险信号2"     }    } 注意：  只提取文档中明确陈述的需求，不要推断  如果发现"待讨论"、"暂不确认"等表述，将 status 设为 pending  如果发现"不实施"、"超出范围"等表述，将 status 设为 outofscope 文档内容： {documentchunk} |

# **第七章  API 接口设计**

## **7.1  RESTful API 规范**

所有 API 基础路径为 `/api/v1`，返回结构统一为：

```json
{
  "status": "success|error",
  "data": {},
  "message": "optional"
}
```

当前实现默认**不启用** JWT 等认证（单机/内网形态）；安全隔离与鉴权属于后续规划，部署侧应通过网络边界/反向代理/访问控制解决。

## **7.3  流式输出（SSE）**

当前实现使用 **Server-Sent Events（SSE）** 返回流式日志与模型输出（`text/event-stream`），典型事件包括：

- `stage`：里程碑开始/结束（例如“解析文档”“片段与来源索引”“思考分析”“呈现结果”）
- `delta`：模型增量输出片段
- `final`：最终 Markdown 与导出路径信息（如可用）

前端据此实现：过程流式展示、里程碑折叠/展开、完成提示与导出按钮。

# **第八章  报告生成引擎详设**

## **8.1  docx 报告生成方案**

报告生成采用 Node.js docx 库（参考已验证的技术方案），在后端服务中通过子进程调用生成 Word 文档，实现专业排版效果。

## **8.2  报告元素规范**


| 元素类型   | 实现规范                               |

| 封面     | 项目名称（大字）+ 报告类型 日期 生成者信息，深色背景营造专业感  |
| 目录     | 自动生成，基于 HeadingLevel，Word 中可更新页码   |
| 正文标题层级 | H1H4，使用 Microsoft YaHei 字体，颜色区分层级  |
| 风险表格   | 彩色表头（深蓝底白字），奇偶行交替浅灰/白色，单元格有内边距     |
| 引用框    | 左边框+浅色背景的信息框，引用原文片段                |
| 统计图表   | 先用 ECharts 渲染为图片，再通过 ImageRun 嵌入文档 |
| 检查清单   | 表格形式，每行含检查项、状态（✅/⚠️/❌）、说明          |
| 页眉页脚   | 左侧项目名称，右侧页码；底部分隔线                  |

# **第九章  部署与运维方案**

## **9.1  部署模式**


| 部署模式       | 适用场景         | 技术方案                              | 说明         |
| ---------- | ------------ | --------------------------------- | ---------- |
| 单机桌面版      | 个人顾问、小团队     | Electron/Tauri SQLite 本地 LLM/API  | 最低依赖，零运维成本 |

## **9.2  Docker Compose 配置（本地服务器版）**


| docker-compose.yml（当前仓库推荐形态） 以单容器/单进程提供前后端同源服务为主：backend（FastAPI + 静态前端 dist）。关键挂载：项目目录（供 docs2md 读取）与 `/app/.tmp`（SQLite/导出/里程碑日志）。若要扩展为多服务（队列、向量库等），属于后续规划与二次集成范围。 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |


## **9.3  安全设计**

- API 密钥加密存储：使用 AES-256 加密，密钥派生自用户密码（PBKDF2）。
- 项目数据隔离：多用户场景下通过 Row-Level Security 保证数据隔离。
- LLM 调用审计：记录每次 LLM 调用的输入输出摘要（可配置是否记录完整内容）。
- 文档内容不上传：当前实现默认不做向量化；仅在本地将片段（chunks）送入配置的 LLM Provider（可能是云端 API），管理员需按企业合规要求配置 Provider、网络与脱敏策略。

# **第十二章  扩展机制：审查技能（Skills）、记忆（Memory）、工具（Tools）、钩子（Hooks）**

> 本章描述**当前仓库已实现**的可扩展点，用于统一产品、帮助文档与代码行为。更细的目录与文件格式约定见 `docs/aika_spec/PACKAGE_LAYOUT.md`、`MEMORY_TAXONOMY.md`、`SKILL_MANIFEST.md`。

## 12.1 审查技能包（Skills）

- **定位**：一套可切换的**审查配置包**，内含 `manifest.json`（id、名称、版本等元数据）与 **`review_domain.md`**（关注点 `### focus:…`、**组合使用建议**五列表等）。与仓库根 `default_skills.md` 结构对齐的部分可迁移/导入到包内 `review_domain.md`。
- **存放位置**：默认在仓库根下 `review_skill_packages/<package_id>/`；可通过环境变量 **`AIKA_REVIEW_SKILL_PACKAGES_ROOT`** 指向其它根目录。
- **运行时选择**：当前活动包 id 保存在应用设置（如 `app_settings.md` / 设置 API）中的 **`active_skill_package_id`**（默认常为 `package-general`）；用户可在 **设置 → 审查域** 切换包。
- **在分析流程中的作用**：发起 `POST …/analyze/stream` 时，后端将关注点解析结果、预设中的审查角色/目标与原则/输出要求、以及技能包相关的 **skill 元数据**（包 id、规则文件哈希等）一并写入 **系统提示词**（`build_system_prompt`），使同一套文档在不同技能包下可有不同审查立场与输出约束。

## 12.2 记忆（Memory）

- **定位**：在审查前向模型提供**可复用的短文本知识**（术语、偏好、项目画像摘要等），与「当前分块正文」分离管理。
- **存放位置**：在 **`AIKA_REPO_ROOT`（仓库根）** 下 **`/.aika/memory/`**，子目录约定为：`user/`、`feedback/`（全局）；`project/<project_id>/`、`reference/<project_id>/`（按项目）。文件为 **Markdown（`*.md`）**；分类与命名约定详见 `docs/aika_spec/MEMORY_TAXONOMY.md`。
- **召回机制**：分析请求可携带 **`memory_snippets`**（直接指定片段）、**`memory_query`**（检索词；未传时后端可用关注点名称拼接）、**`already_surfaced`**（已注入 id 去重）。服务端在候选文件中做**关键词分词重叠打分**，取不超过 **5** 条正文（有长度上限），拼入系统提示中的 **「【注入记忆片段】」** 段落（见 `prompt_builder.py`、`memory_recall.py`）。
- **API**：`GET /api/v1/projects/{id}/memory/files` 列出可用相对路径；`POST …/memory/upsert` 在允许前缀下写入/更新单个 `.md` 文件。
- **审计**：运行元数据中记录 **`memory_files_injected`**（路径 id 与标题摘要），便于复现本轮注入了哪些记忆文件。

## 12.3 工具（Tools）

- **定位**：后端维护 **Tool 注册表**（`backend/tools/registry.py`），通过名称调用，用于校验、指标计算等**不替代主 LLM 审查**的辅助逻辑。
- **调用方式**：HTTP **`POST /api/v1/tools/invoke`**，body 含 `name` 与可选 `kwargs`；返回统一结构（含 `status`）。
- **预设工具（示例）**：如 **`validate_review_domain`**（校验审查域文本模式）、**`compute_scope_metrics`**（占位类统计）等；可按需注册新工具，**不应**在工具内重复实现与主流程相同的审查逻辑。

## 12.4 钩子（Hooks）

- **定位**：在**单次会话分析**（`analyze/stream`）前后插入扩展逻辑，用于审计、或向上下文追加额外记忆片段等。
- **扩展点**：**`run_before_analyze_hooks(ctx)`**（构建系统提示前）、**`run_after_analyze_hooks(ctx)`**（落盘与入库完成后）。`ctx` 至少包含 `project_id`、`conversation_id`、`focus_points`、`chunk_limit`；before 阶段可写入 **`ctx["extra_memory_snippets"]`**（元素为 `{id,title,body}`），由主流程合并进本轮 `memory_snippets`。
- **内置行为**：默认注册**审计日志**（logger `aika.hooks.audit`），不修改业务数据。
- **错误策略**：单个 hook 抛错时记录日志，**不中断**主分析流程（详见 `backend/hooks/registry.py`）。


# **附录 A  术语表**


| 术语                   | 定义                                    |
| -------------------- | ------------------------------------- |
| Chunk                | 文档被切分后的最小语义单元，通常为 512-2048 tokens     |
| Embedding            | 将文本转换为高维向量的过程，用于语义相似度计算               |
| 标注（Annotation）       | 从文档中提取的结构化信息条目，可由 AI 自动生成或人工手动创建      |
| 知识条目（Knowledge Item） | 从标注中提炼的、可跨项目复用的行业洞察                   |
| 分析任务（Analysis Job）   | 一次 LLM 调用任务，对一组文档进行特定类型的分析            |
| 健康度评分                | 基于多维度指标（需求覆盖率、风险数量、任务追溯完整性等）计算的项目综合评分 |
| LLM 网关               | 统一封装不同大模型提供商的适配层，对上层业务屏蔽模型差异          |
| Go/No-Go 评审          | 上线前的决策门控会议，逐条核查上线条件是否满足               |
